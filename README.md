# Sample microservices on OCI Always Free

```
                     Internet
                        │ :80
          ┌─────────────▼──────────────┐
          │ OCI Flexible LB (10 Mbps)  │  Always Free, health check GET /healthz
          └──────┬──────────────┬──────┘
                 │              │
   FAULT-DOMAIN-1│              │FAULT-DOMAIN-2
 ┌───────────────▼───┐      ┌───▼───────────────┐
 │ vm-1  A1 2c/12GB  │      │ vm-2  A1 2c/12GB  │
 │ nginx :80         │      │ nginx :80         │
 │  /api/catalog/* ─►catalog │  /api/catalog/* ─►catalog
 │  /api/orders/*  ─►orders  │  /api/orders/*  ─►orders
 │  /              ─►static  │  /              ─►static
 │ postgres PRIMARY ─┼─WAL──┼─► postgres STANDBY │
 │ db-watchdog       │      │ db-watchdog       │
 └───────────────────┘      └───────────────────┘
```

Everything runs in Docker Compose on Ubuntu 24.04 (aarch64), provisioned by cloud-init.

## What stays free

| Resource | Used | Always Free limit |
|---|---|---|
| Ampere A1 compute | 2 VMs × 2 OCPU / 12 GB | 4 OCPU / 24 GB total |
| Boot volumes | 2 × 50 GB | 200 GB total |
| Flexible load balancer | 1 × 10 Mbps | 1 × 10 Mbps |
| VCN, IGW, NSGs, public IPs | yes | free |

Don't raise `vm_ocpus`, `vm_memory_gbs` or `boot_volume_gbs` beyond these totals.

**Idle reclamation:** Oracle may reclaim Always Free A1 VMs that stay idle for 7 days
(CPU, network and memory all under ~20%) on accounts that haven't been upgraded to
Pay-As-You-Go. Upgrading to PAYG keeps Always Free resources free and removes reclamation.

## Deploy

```sh
export VAULT_ADDR=https://vault.naidu72.info VAULT_TOKEN=...   # provider.tf reads OCI creds from Vault
cp terraform.tfvars.example terraform.tfvars                   # set admin_cidr to your IP/32
terraform init
terraform plan
terraform apply
terraform output app_url
```

VMs take ~5 minutes after apply to install Docker and build the images. Then:

```sh
URL=$(terraform output -raw app_url)
curl $URL/api/catalog/products
curl -X POST $URL/api/orders/ -H 'Content-Type: application/json' -d '{"product_id": 1, "quantity": 2}'
curl $URL/api/orders/
curl $URL/api/catalog/health     # shows which VM served it and which DB node is primary
```

`Out of host capacity` for A1 is common; retry later or change `availability_domain_index`.

## High availability

- **Web/app tier:** the load balancer health-checks both VMs and drops a VM whose nginx
  or app stops answering. Each VM is in a different fault domain, and OCI restarts
  the instance after host maintenance (`recovery_action = RESTORE_INSTANCE`).
  All containers use `restart: unless-stopped`.
- **Database tier:** vm-1 runs the primary, vm-2 a streaming hot standby. Both apps list
  both DB hosts with `target_session_attrs=read-write`, so they always write to whichever
  node is currently primary.
  - If the primary is unreachable for `failover_after_seconds` (default 60), the watchdog
    on the standby promotes it.
  - When the old primary returns, it sees its peer on a newer timeline, moves its data to
    `pgdata.stale-<timestamp>` inside the volume, and re-clones as a standby.

**Caveat:** with only two nodes there is no quorum. If the VMs lose contact with each
other but both stay up, both can accept writes for a short time; when they reconnect,
the newer timeline wins and writes made to the other node in that window are discarded
(kept in the `pgdata.stale-*` directory). For stronger guarantees, add a third witness
(e.g. an Always Free `VM.Standard.E2.1.Micro`) and use Patroni, or switch to the
Always Free Autonomous Database.

## Operating

```sh
ssh ubuntu@<vm-ip>
cd /opt/app && sudo docker compose ps
sudo docker compose logs -f db
journalctl -u db-watchdog -f
sudo docker exec db psql -U postgres -c 'select pg_is_in_recovery()'         # t = standby
sudo docker exec db psql -U postgres -c 'select * from pg_stat_replication'  # on the primary
```

Manual switch-over: stop the primary's db (`sudo docker compose stop db`), wait for the
watchdog to promote the other node, then `sudo docker compose start db` to rejoin as standby.

Terraform ignores changes under `app/` on running VMs (cloud-init only runs on first boot,
and replacing both VMs at once would take down the database). To roll out app changes,
either copy them to `/opt/app` on each VM in turn and run `sudo docker compose up -d --build`,
or rebuild one VM at a time, letting the database re-sync in between:

```sh
terraform apply -replace='oci_core_instance.node["vm-2"]'
terraform apply -replace='oci_core_instance.node["vm-1"]'
```

Secrets are generated by Terraform (`random_password`), stored in Terraform state and in
`/opt/app/.env` (mode 600) on each VM. Keep your state file private.
